## 2026-07-16: 상태 카드가 와이파이 신호를 놓치자마자 "자리비움"으로 바뀌는 문제 수정

- **사용자 지시**: "자리비움 처리가 이상하다. 와이파이 신호를 놓치자 마자 자리비움으로 가는게 아니다. 자리비움 설정시간만큼 지났을때 그 때 자리비움 기록이 되어야 한다."
- **원인 분석**: 실제 DB 이벤트 기록(`WifiMonitorService.checkWifiState()`)은 원래부터 정확했음 — 자리비움/퇴근 이벤트는 항상 자리비움 인정 기준(기본 10분)이 지난 뒤에만 기록되도록 이미 구현돼 있었음. 문제는 **상태 카드에 표시되는 실시간 라벨**(`MainActivity.kt`의 `commuteStatus()`)이었음 — `isAtWork && !detectedNow`이기만 하면(즉 와이파이가 안 잡히는 바로 그 순간부터) 유예 기간과 무관하게 즉시 "자리비움"으로 표시되고 있었음. 실제 기록은 맞는데 화면 라벨만 성급하게 바뀌는 표시 전용 버그.
- **수정**:
  - `CommuteViewModel.kt`에 `awaySinceAt: StateFlow<Long?>` 신설(`settingsRepository.awaySinceAt`를 그대로 노출 — 백엔드가 자리비움 유예를 재는 것과 동일한 실제 값을 그대로 씀, UI에서 별도로 다시 계산 안 함).
  - `MainActivity.kt`: `CommuteScreen`에서 `awaySinceAt`, `absenceThresholdMinutes`(이미 있었지만 안 쓰고 있었음)를 새로 수집. `commuteStatus()` 시그니처에 이 둘을 추가해서, `awaySinceAt`이 null이거나 `now - awaySinceAt < 임계값`이면(아직 유예 중이면) `isAtWork && !detectedNow`여도 "자리비움"이 아니라 그대로 "근무중"으로 표시. 임계값을 실제로 넘은 뒤에만 "자리비움"으로 전환. `CompactStatusCard`에도 두 파라미터 추가해서 그대로 전달.
  - 점심시간 특수 로직(점심시간 중엔 아무리 오래 끊겨도 퇴근 처리 안 함)은 이 계산에서 별도로 신경 안 씀 — 점심시간이어도 자리비움 인정 기준을 넘으면 "자리비움 · 점심시간"으로 표시되는 게 자연스럽다고 판단(기존에도 `isLunchTimeNow`가 별도 접미사로 붙는 구조라 자연히 맞물림).
- **실기기 검증**: 재빌드(`assembleDebug`)+재설치(`installDebug`) 후 앱 강제종료→재실행, 크래시 없음. 현재 회사 와이파이 연결 상태에서 상태 카드가 "근무중"으로 정상 표시되는 것 확인. (실제로 와이파이를 끊고 유예 기간 동안 "근무중"이 유지되다가 임계값을 넘는 순간 "자리비움"으로 바뀌는 것까지는 실기기를 물리적으로 이동시켜야 재현 가능해서 이번엔 코드 로직 검토로 갈음 — adb만으로는 재현 불가.)
- **How to apply**: 이 앱은 "실제 기록되는 이벤트"와 "화면에 보여주는 실시간 상태"가 서로 다른 계산 경로를 갖고 있어서, 데이터 기록 로직이 맞다고 해서 화면 표시 로직도 맞다는 보장이 없음 — 사용자가 "이상하다"고 느끼는 지점이 항상 DB 로직이 아니라 표시 로직(`commuteStatus`, `MainActivity.kt`)일 수 있다는 걸 염두에 둘 것. 다음에 비슷한 "화면에 보이는 상태가 이상하다"는 리포트가 오면 `WifiMonitorService`보다 `MainActivity.kt`의 상태 계산 함수부터 먼저 볼 것.

## 2026-07-16: 자리비움/퇴근 정책 전면 재정의 — 하루 1회 출퇴근, 초과 자리비움은 근무시간에서 차감

- **경위**: 자리비움 설명을 두 라운드에 걸쳐 다시 주고받으며 사용자가 최종 확정한 정책. 계기가 된 질문: "외부 회의 갔다가 복귀하면, 자리비움 인정 기준(예: 10분)을 넘겨도 이전 퇴근 기록이 지워지나? 아니면 복귀 시 새 출근이 기록되나?" — 기존 코드(자리비움 인정 기준을 넘기면 그날 안에서도 바로 퇴근+재출근 쌍으로 기록)를 정확히 설명했더니, 사용자가 "이상하다"며 정책을 새로 확정: **"하루에 출근/퇴근은 각각 한 번만. 복귀 시에는 그냥 자리비움 해지가 되는 것 — 자리비움 인정 기준이 30분인데 1시간 있다 복귀해도 자리비움 1시간으로 기록되어야 한다."**
- **확정된 새 정책**:
  1. 하루에 ARRIVE/LEAVE는 각각 정확히 1번만 기록됨.
  2. 낮 동안 와이파이가 끊겼다가 같은 날 안에 다시 잡히면 — **끊긴 시간이 자리비움 인정 기준을 넘든 안 넘든 상관없이** — 무조건 자리비움(AWAY)으로 기록되고(실제 전체 지속시간 그대로), 세션은 계속됨. 더 이상 "기준 초과 시 그 자리에서 퇴근 확정" 로직 없음.
  3. 자리비움 인정 기준(분)의 역할이 "퇴근이냐 아니냐를 가르는 기준"에서 "그 자리비움이 근무시간에서 빠지느냐 마느냐를 가르는 기준"으로 바뀜 — 점심시간 차감과 동일한 방식. 기준 미만 자리비움은 근무시간 그대로 인정, 기준 이상 자리비움은 근무시간에서 차감(단, 점심시간과 겹치는 부분은 이중 차감 방지를 위해 그 부분 제외).
  4. 퇴근(LEAVE)은 오직 "자정을 넘겨도 그 단절이 재확인되지 않았을 때"(day-boundary 안전장치)만 기록됨 — 마지막으로 확인된 시각을 기준으로.
- **구현**:
  - `WifiMonitorService.kt`: `checkWifiState()`에서 자리비움 인정 기준·점심시간 유예 로직을 이용한 "당일 즉시 퇴근 확정" 브랜치를 완전히 제거. 재연결 시 무조건 AWAY 기록(지속시간 무관). 그 결과 `isWithinLunchWindow`/`lunchEndTimestampIfPassed`/`lunchWindowMinutes`/`minuteOfDay` 헬퍼 전부 죽은 코드가 되어 삭제, `timestampAtMinuteOfDay` import도 제거. day-boundary 안전장치(자정 넘어도 안 풀리면 `lastSeenAt` 기준 강제 퇴근)는 그대로 유지 — 이게 이제 LEAVE를 만드는 유일한 경로.
  - `WorkStats.kt`: `computeDailyWorkStats`에 `absenceThresholdMinutes: Int` 파라미터 신설. 세션(ARRIVE~LEAVE) 안의 AWAY 이벤트들을 수집해서, 각 AWAY 지속시간이 기준 이상이면 그 시간(점심시간과 겹치는 부분은 `lunchOverlapMinutes`로 빼고) 만큼 근무시간에서 차감. 기준 미만인 AWAY는 그대로 근무시간으로 남음.
  - `CommuteViewModel.kt`: `dailyWorkStats`의 `combine`에 `settingsRepository.absenceThresholdMinutes` 추가(5개 Flow까지는 `combine` 람다 오버로드로 충분).
  - `README.md`: 출퇴근 자동 기록/자리비움 구분/점심시간/근무시간 계산 설명을 새 정책에 맞게 재작성.
- **실기기 검증**: `assembleDebug`+`installDebug` 성공, 강제종료→재실행 크래시 없음, 서비스 정상 기동. 현황 탭에서 "근무중" 상태와 오늘/이번주 근무시간이 정상 표시되는 것 확인(기존 데이터 기준 5시간59분/31시간37분, 회귀 없음). 설정 화면의 자리비움 인정 기준 드롭다운도 정상 렌더링·동작 확인(10분~3시간 11단계, 현재 값 30분 정상 표시).
- **아직 라이브로 재현 못 한 것**: 실제로 기준을 넘는 장시간 이탈 후 복귀했을 때 자리비움으로 기록되고 근무시간에서 정확히 차감되는지는 물리적으로 와이파이 범위를 벗어났다 돌아와야 확인 가능 — adb만으로는 재현 불가, 코드 로직 검토로 갈음.
- **How to apply**: 이 정책 변경으로 `자리비움 인정 기준` 설정의 의미가 근본적으로 바뀌었음("퇴근 트리거"→"근무시간 차감 트리거") — 이후 관련 질문/버그 리포트가 오면 이 새 의미를 기준으로 판단할 것. [[project_gasan_labor_policy]] 계열 문서(다른 대화의 공유 메모리)에도 이 정책 변경을 반영해야 할 수 있으니, 다음에 그 메모리를 다루는 대화가 있으면 이 파일을 참고해 동기화할 것.
